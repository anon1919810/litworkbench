# 下一轮：OCR 候选对照与采用

2026-10-16。状态：设计提案；本轮只形成设计、可点击草图和实施分工，不修改产品运行代码。承接已完成的 [真实样本评估](../../ocr-quality-evaluation.md) 与既有 [网页设计](2026-10-15-web-workbench-design.md)。

## 1. 本轮要解决的使用场景

用户检索某文化遗产，发现原页存在的专名或数字没有命中，进入阅读器选中该页，尝试另一种识别配置；识别完成后先对照原图与现用文字，再决定是否采用。用户可以放心试，不会因新 OCR 较差而失去旧文字、人工校订及摘录。

这一轮把已有 OCR 实验变成网页内可操作的校核闭环。沿用用户确定的本地优先、中文、Notion 式白底侧栏；不新增独立“AI 控制台”。日常操作不需要 CLI、AI API 或 OpenCode。

以下为 Codex 根据实测提出的方案，不冒充用户已经确认的细节：默认生成待确认候选；小批次作为第一接入配置；复杂模型和多栏排序分后续小阶段进入。

## 2. 为什么按这个顺序

| 实测事实 | 设计决定 |
| --- | --- |
| small 批次 1 的关键词命中从 24/28 到 25/28，5 页暂定参考距离 24→23 | 先接入低资源配置，无新增识字权重依赖 |
| 相同批次/线程下 medium 为 19 错，较 23 错下降 17.39%，没有新增关键词命中 | 后续可选精细识字，不承诺“高精度”，不自动替代默认 |
| GapTree 修复两页强制 OCR 双栏，但一页单栏标题退化 | 必须明确选择双栏，产生独立候选，不自动识别版面后全库套用 |
| Docling 全层导出仍有标题顺序和标点变化 | 下一轮不接入产品默认，不扩展通用多引擎架构 |
| Windows 提交额度曾耗尽 | 串行、受控子进程、资源上限与明确失败原因先于提速 |
| 参考稿全是 agent_checked，7 页有未决字 | 产品不显示“准确率 99%”等数字；人工核对与模型置信度分开 |

## 3. 用户能看到的页面

### 3.1 阅读器里的入口

现有“重新识别”按钮扩展为“生成识别候选”。弹窗只问三件事：处理哪些页、用哪种识别方式、是否需要双栏顺序。第一阶段支持“兼容配置”“省资源配置”；多栏和 medium 在后续阶段可用时才出现，不用不可操作选项填满界面。

- 范围默认本页。可指定文件页范围或整份 PDF，提交前展示解析后的实际页数；文件页不是印刷页。范围限定一个文献，后端验证显式 unit_id，首轮最多 1000 个去重页。
- 省资源配置说明为“逐页处理、减小单次识字批次”，不把运行更稳定等同于识别一定更准。
- 按钮是“生成候选”，完成后为“待核对”，不显示成已采用。候选产生前不改变当前检索和摘录。
- 已存在“直接重新识别”后端路径保持旧调用兼容；网页入口转为候选流程，显式提示语义变化。旧导入任务与既有直接识别任务不在此次迁移中悄悄改义。

### 3.2 原页与候选对照

沿用 Reader 的原件/文字/对照空间。在对照方式中增加候选选择与差异开关。宽屏左侧为原页，右侧在“现用文字 / 候选文字”间切换；需要同时核对时展开为原页、现用、候选三个区域。窄屏保留原图/现用/候选标签，不把文字挤成三条细栏。

原图始终保留缩放、文件页序、印刷页码确认状态。文字差异以插入/删除/替换标记呈现，可跳转上/下一处；颜色必须配合文字标签。差异多只表示不同，不宣称更正确。模型名、模型指纹、原始框、耗时与资源细节放在可展开“识别详情”。

固定操作为“保留现用”“采用候选”。没有候选、运行中、失败、冲突状态均不给可误用的采用按钮。批量生成可以，第一阶段逐页采用；不做默认勾选后整库一键替换。

### 3.3 有人工校订时

“现用文字”明确标注人工校订。采用候选仅更新机器 OCR 层，人工校订继续作为现用文本，不被自动抹掉。采用区显示“更新识别底稿；人工校订仍用于检索”。若要把候选中的字合入现用文字，走既有校订编辑器并填写原因，产生独立人工校订历史。

比较时可切换“现用文字”和“旧 OCR 底稿”，避免把人工改字误认为模型退化。摘录只能从当前有效版本保存，未采用候选上不直接保存正式摘录。

### 3.4 任务与待核页

复用识别任务页，区分运行计数“完成候选 8/10 页”和人工处理计数“待核对 8 页”。暂停/继续、失败重试沿用检查点，关闭网页不取消后台任务。任务完成可直接跳到第一个待核页；阅读器内也可转到同任务下一待核页，保留文献和文件页定位。

资源不足显示“本页识别因内存上限停止，旧文字仍可用”，提供查看详情、用省资源配置再试。超时、缺模型、空结果与进程异常分别说明。失败页不混入待核候选，不显示零秒或零内存代表成功。

## 4. 候选与现用文字的关系

新增独立的候选记录，不把它塞入 corrected_text，也不让候选表参与默认 FTS 索引。候选创建、识别完成、人工采用是不同事件。

生命周期：任务页 queued → running → ready / failed；ready → adopted / rejected / stale。运行结束前采用操作不可用。人工丢弃只标 rejected，保留记录，不物理删除结果。被采用的候选仍保留完整结果和人工决定时间。

每次候选尝试具有独立 attempt_id；重试新增尝试，不覆盖前一次失败记录。每页至多一个活动尝试，用数据库约束保障。恢复时将崩溃遗留的 running 尝试终结为带 interrupted 错误的失败记录，再创建新尝试。ready/adopted/rejected/stale 都表示该页推理已完成，恢复不能重做；待核数只计 ready，与推理完成数分开。

执行令牌是 owner + claim_generation，提交候选再校验 attempt_id。候选完成与 job_units 完成在同一事务提交。续租、更新阶段、写检查点、提交页结果、终结任务均须校验令牌，不能仅在最后结果写入时检查。丢失执行权的旧 worker 不得续租、改进度或终结新 worker 的任务。新增 kind 的计数按 job_units/候选状态显式处理，不能落入旧 import 的文献页计数分支。

候选数据至少包括：

| 字段组 | 内容 |
| --- | --- |
| 身份 | candidate_id、job_id、attempt_id、unit_id、doc_id、source_sha256、file_page |
| 基础版本 | 生成时的 unit content_revision、旧 OCR 文本哈希、校订文本哈希（含 null 区别）、有效文本哈希与状态 |
| 配置 | profile_id + profile_version、参数快照及哈希、渲染倍率、模型文件 SHA-256、运行版本、布局选择 |
| 结果 | 原始模型行/框/真实置信度、排序后文本与行序映射、坐标约定、实际渲染尺寸、文本哈希 |
| 执行 | queued/running/ready 等状态、初始化/识别耗时、RSS/private 采样、错误种类、受控超时、时间戳 |
| 决定 | adopted/rejected/stale、决定时间、采用前后版本、原因、执行者令牌 |

原件不变；机器原始行输出与排序派生结果分别保留。双栏后处理不能就地改写原始行数组，不能丢页眉、页码、标点或专名。没有框或真实置信度则 null 并说明，不编造。

## 5. 采用事务与并发

新增页内容修订号 content_revision，以单调整数表示与候选有关的页面内容变更。机器 OCR、人工校订及空白页状态变更均推进；相同文字但模型/配置/来源变更也推进，保证来源审计不被静默覆盖；初始化旧库为 0。仅修改书目或印刷页码不改变内容号，采用时保留事务内读到的最新元数据。

修订号保障集中在存储边界，覆盖 save_unit、校订、确认为空白及全部既有写入口，不能要求各业务入口自行记得加一。旧 set_printed_page 的“读整页后整行回写”需改成只更新页码字段；任何元数据 setter 都不能把旧文字回写覆盖并发采用或校订。并发测试必须证明“修改页码不回退文字、不推进内容号”。迁移在启动新版 worker 前完成，先备份再迁移，不允许旧版 worker 与新版模式混跑。

采用在同一 SQLite 写事务里完成：

1. 先识别同一候选已采用的幂等重试，返回原采用结果，不重复变更版本。
2. 验证 candidate 属于当前 unit、源 PDF 哈希与页序未变、状态为 ready，且请求期望修订号 = candidate 基础修订号 = 当前 content_revision。
3. 保存采用前机器 OCR 层的不可变快照，包含旧原文、ocr_json、来源/模型指纹（历史未记录的标 unknown，不事后补造），然后原子更新机器 OCR 和来源元数据、保留校订与页码、新增历史、推进修订号、记录采用。禁止 INSERT OR REPLACE 触发父表级联删除。
4. 候选中包含非空白文字但源文件变化、页面被确认为空白或修订号变化时返回 409，旧文字不动。首轮冲突候选只可保留查看、重新生成，或通过校订器手工合入；不做重新绑定基础版本后的采用接口，也不提供无检查的“强行覆盖”。
5. 同页其他 ready 候选标为 stale，已采用/丢弃记录不改写。迟到完成的旧候选按当前内容号标 stale。
6. 采用事务记录索引待更新及摘录复核信息。索引只指向现用文字，失败时沿用 dirty 页可见性机制补偿；不能在候选刚生成时提前索引。

旧摘录原文、偏移、版本快照和集合关系始终保留。按其实际依赖版本判断是否需复核；校订有效文本未变化时，不能把该版所有摘录一律失效。索引及复核逻辑应复用已有服务或抽出可传同一 connection 的事务入口，不复制两套语义。

## 6. 模型、资源与后台边界

首轮 profile 是稳定枚举，后端不接收任意模型路径、Python 路径或可执行脚本：

- `compatible-v1`：保留当前默认 RapidOCR 行为。
- `small-lowmem-v1`：现有 small 检测/识字、分类批次 1、识字批次 1、ONNX intra/inter 各 2、render_scale=2。默认仅用于新建候选，尚不修改新导入的全局默认。
- 后续 `medium-lowmem-v1`：同检测、线程、批次，只换固定 medium 识字权重；缺模型返回明确状态。双栏排序是独立布局选项，记录算法提交与行序映射。

每个候选页在受控子进程内渲染与 OCR，父 worker 负责租约、检查点和采样；只终止自己启动的进程树。复用评估中已验证的超时和资源控制思路，将需要的最小实现放入产品模块，不让产品 import scripts/ocr_quality。PDFium 仅在子进程内串行运行；原图预览保持已有隔离渲染路径。

首轮按评估配置使用初始化 120 秒、识别 60 秒、RSS/private commit 2.5 GiB 上限，开发配置可调但网页不暴露自由参数。资源采样在产品中需要显式、可锁定依赖；若采样不可用，任务启动即报“资源保护不可用”，不能偷偷无上限执行或写假零。适配资源控制的 psutil 必须经依赖评审与锁更新，不能靠评测目录的临时 PYTHONPATH 启动产品。

一个后台执行者一次执行一页，控制引擎生命周期。另加**工作区级 OCR 执行闸门**，覆盖新候选与既有后台 import/reprocess OCR；多 worker 领取不同任务仍只能有一个受控 OCR 页执行。闸门使用可恢复租约和代次令牌，旧页进程确认结束或被终止后才能释放/转交；不能只因租约到期就容许两个仍存活的 OCR 子进程并行。纯索引任务不占此闸门。每个进程各自的 2.5 GiB 上限不能替代工作区串行保障。

若将来缓存引擎，缓存键须包含模型及参数指纹，不可让当前单例 _ENGINE 跨配置复用。本轮不做多进程加速或共享全局配置热切换。

原始结果落盘采用任务自有受控目录和原子提交，路径从稳定 ID 生成；文件存在、链接、路径穿越及源目录边界检查沿用评估修复，不从请求接收任意输出路径。失败原始结果可诊断，数据库不会指向未提交半文件。

## 7. 拟新增 API 与模块责任

以下是可供施工的接口提案，尚未实现；正式实施计划还需列迁移及测试细项。

| 接口 | 行为 |
| --- | --- |
| GET /api/v1/ocr/profiles | 稳定配置、可用性与原因；不回显本机绝对模型路径 |
| POST /api/v1/documents/{doc_id}/ocr-candidate-jobs | unit_ids、profile_id、layout；验证页范围与快照后 202，返回 job_id |
| GET /api/v1/units/{unit_id}/ocr-candidates | 分页列候选摘要、状态、基础修订号；可按 job_id 筛选 |
| GET /api/v1/ocr-candidates/{id} | 结果详情、哈希、来源及差异所需文本 |
| POST /api/v1/ocr-candidates/{id}/adopt | expected_content_revision；ready 且版本匹配才采用；幂等 |
| POST /api/v1/ocr-candidates/{id}/reject | 标记保留现用及可选原因；幂等，不删除审计 |

沿用本机会话、Origin/CSRF、JSON 错误与分页上限。请求严格拒绝未知 profile/layout、Word 单元、跨文献页、负数页、空集合与超过范围。job 使用既有任务控制接口，新的 kind 具有独立 handler，不改变旧 reprocess 的已承诺行为。

新增深度适中的候选服务封装存储与采用事务；OCR profile/受控推理负责产出，不直接写 units。Web 层只校验和排队；Reader 只展示、比较与发出决定，不持有后台任务的真相。字段命名可由执行者在这一边界内定，但不得扩大为插件框架。

## 8. 拆成可验收的实施单元

| 顺序 | 交付 | 独立验收重点 |
| --- | --- | --- |
| A | 候选存储、内容修订号、创建/采用/丢弃事务 | 旧库迁移不丢证据；生成不改现用；采用 CAS、幂等、修订冲突、人工校订及集合保留 |
| B | 两种 small 配置、受控 worker、队列恢复 | 真实单页产物与模型指纹；资源/超时保护；迟到执行者拒绝；任务恢复不重复 ready 页 |
| C | 阅读器弹窗、候选对照与待核导航 | 键盘/窄屏；晚返回结果不串页；失败/冲突按钮状态；只从现用文字保存摘录 |
| D | 12 页真实回归、来源/校订/摘录/索引核对 | 在独立验收工作区跑；候选前后真实库不写；采用前后有效文字、FTS 与复核状态吻合 |
| 后续小阶段 | medium 与明确双栏排序 | 原始行集合保持；原先正确单栏标题不默认被排序；不以不同参数控制组冒充模型收益 |

人工参考核稿、坏文本层和表格补样与上述开发并行安排；1000 页容量、检索 p95 和长任务恢复仍须真实资料验收，不能拿重复页拼接冒充。

Codex 负责设计、任务简报、代码审查与独立验收；OpenCode 负责每个有界实现单元。每个单元最多两轮缺陷反馈，再由 Codex 收回重划范围。核心数据事务不能因为模型免费就交给无人审查的长循环。
