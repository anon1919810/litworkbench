# 县志 OCR 实测与接入决定

2026-10-16。本轮完成评估工具、真实样本对照和本地网页报告。结论是保留现有默认 OCR；减小批次值得优先接入验证，medium 识字模型及双栏排序只进入局部增强候选。尚未修改产品 OCR 默认设置。

## 样本与指标边界

真实资料库有 6 份 PDF 摘选文件、合计 91 页，并非六本完整长书。从每份选两页，共 12 页：10 页扫描件、2 页可检索文本层，含《安康县志》文件第 7 页。源文件、文件页序、单页派生 PDF、渲染图、参考稿与模型均保留身份和 SHA-256。印刷页候选不自动成为确认页码。

12 份参考稿都经过代理对照原图，标记为 `agent_checked`，**没有人工金标准**。其中 7 页有尚未确定的字，整页不参与 CER；共同可评分集合为其余 5 页、4291 个非空白字符。CER 只去空白，保留标点、数字和生僻字，按参考字符数加权。不可把此结果表述为整库准确率或 1000 页验收。

检索使用产品的 SQLite FTS5 phrase 路径，在独立临时库中验证 28 个阳性 query-page 对及 19 个近似词阴性案例。所有 12 页保留运行状态；不能把未评分页当成零错误。两个文本层页在 auto 模式直接取文本，并另做强制 OCR 顺序实验。

同批次控制很关键：原默认到 medium 组合少了 5 个字符错误，但其中 1 个改善及“父母之命，媒妁之言”的检索恢复，在 small 模型批次改为 1 时已经出现。严格只比较相同批次和线程，medium 从 23 错降至 19 错，相对下降 **17.39%**，未达到计划中 20% 的自动推荐门槛，也没有额外关键词收益。

## 阅读顺序与来源保真

实际复用了 [Umi-OCR](https://github.com/hiroi-sora/Umi-OCR) 固定提交中的 [GapTree](https://github.com/hiroi-sora/GapTree_Sort_Algorithm) 算法，对已有 RapidOCR 行框排序。上游 MIT 许可已保留，实验确认排序前后完整行对象多重集合一致，没有删文字、框或置信度。

- 两页双栏强制 OCR：原先按整行横穿两栏；GapTree 在两页都恢复了先左栏后右栏的次序。
- 十页单栏扫描：九页次序不变；`book06-p001` 将标题排序到错误位置。因此不全局启用。
- 两个双栏页的原文本层 auto 路径已有合理顺序，不能用强制 OCR 的问题冒充当前 auto 的缺陷。两页参考仍有未决字，顺序改善是对照原图的局部结论，不是全文 CER 证明。

Docling 的结构化原始输出保留页眉和页码，但默认纯文本导出会省略部分内容。改用全部标签、全部内容层及图片子项导出后，省略有所减少，顺序问题仍在：`book06-p001` 将“民俗 宗教 方言”、章题与开篇介绍移到了页末，且将弯引号输出为直引号。171 个编辑距离不能全归因于识字模型，其中文本重排和标点变化也计入。文献逐字摘录需要保真，不能为降低分数而事后归一化这些差异。

## 资源、耗时与失败记录

此处“内存”指运存 RAM 及 Windows 的提交额度，不是硬盘容量。测量同时保留进程树 RSS 与 Windows private commit 峰值；后者不是物理 RAM 用量。每次采样取存活进程树之和，再取历次最大值；共享页可能重复计数，短峰可能漏采，均不是精确系统峰值。

全部最终 OCR 页都实际完成了资源采样。文本层直取不启动受控 OCR 子进程，资源字段按不可用说明，不能写成零占用。监控依赖 psutil 7.2.2 放在独立 `measurement-tools` 目录，通过父进程 `PYTHONPATH` 使用，没有安装进产品主环境。

每页在引擎初始化后连续运行三次，记录初始化、渲染、识别中位数和最大值。**第一次推理可能仍有惰性初始化或冷缓存成本，本轮不是严格预热后的性能基准。** 页面识别耗时中位数的范围：当前默认约 0.97–4.63 秒，medium 约 4.25–8.55 秒。Docling 自行渲染及版面解析，分项不可直接与 RapidOCR 相减比较；其单页进程初始化也需计入实际成本。不得据此给出精确 1000 页工时承诺。

初步高倍率和 medium 检测组合曾在 Windows 提交额度不足时出现 MemoryError，并保留了失败记录。随后仅终止本工具自有的实验进程树，加入 private commit 闸门，串行完成最终对照。没有关闭用户程序或删除用户文件。倍率 3/4 的完整对比尚未完成，高倍率失败不能当作识别质量下降的证据。本轮维持倍率 2，不宣称已找到最优 DPI。

按本机资源收紧了原计划闸门：最终每页 60 秒、初始化 120 秒，RSS/private commit 限额 2.5 或 3 GiB（实际配置见各 run.json），而非原设想的 8 GiB。原始失败、超时与不完整运行保留在 runs 中，主报告明确只纳入五个指定的完整方案，不把诊断运行混为独立样本。

## 复用来源与隔离

本轮核对了 RapidOCR、Docling、PaddleOCR、Umi-OCR、OCRmyPDF、OmniDocBench、OpenOCR、Surya、MinerU 九个官方仓库，具体提交与用途见 [GitHub 调研](ocr-github-research-2026-10-16.md)。实际试用了现有 RapidOCR、官方 medium 权重、GapTree 和 Docling，不是集成九套框架。

- 主环境：Python 3.12.14、RapidOCR 3.10.0、ONNX Runtime 1.31.0、pypdfium2 5.14.0。基线实际是 PP-OCRv6 small 检测与识字。
- Docling：独立环境，docling-slim 2.139.0、docling-core 2.101.1、torch 2.10.0+cpu，83 个依赖按下载 URL 与 SHA-256 锁定。使用官方 PDFium 后端绕过默认 C++ 后端对中文环境路径的资源加载失败。
- 同一路线固定原有三份 ONNX 权重；布局模型 Heron 固定 revision `8f39ad3c0b4c58e9c2d2c84a38465abf757272d8`，六个缓存文件逐项校验，离线模型运行，未启用远程服务。
- 独立候选环境的文件逻辑体积约 1.253 GiB、布局缓存约 0.160 GiB、额外 medium 权重约 0.129 GiB；不包含包管理器下载缓存，也不等于文件系统实际占用。
- 原 PDF 没有发送至在线演示、远程 OCR 或 AI API。候选依赖未装进主环境；主产品源代码和主依赖锁未因本轮评估修改。

评估工作流复现（在产品根目录，使用现有主环境绝对 Python 路径）：

```powershell
python -B -m pytest tests/quality -q -p no:cacheprovider
python -B -m scripts.ocr_quality.prepare --validate ../../work/ocr-quality/2026-10-16/samples.json
python -B -m scripts.ocr_quality.run --help
python -B -m scripts.ocr_quality.report --help
```

重新跑模型时必须使用新的空输出目录，父进程设置独立 measurement-tools 的 PYTHONPATH；候选另传 candidate-python，并设置记录中的 HF_HOME 与 HF_HUB_OFFLINE=1。参数和完整命令见每页记录，不覆盖已有运行。报告过期校验同时检查输入、来源、参考版本和 run_id；过期时 CER 与检索命中数均停用，不能展示旧成绩。
